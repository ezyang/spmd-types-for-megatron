Using spmd_types in Megatron

spmd_types is a type system for distributed tensor computations. It helps solve two specific problems that commonly arise when writing distributed code:

  1. When using differentiable collectives (e.g., as popularized by Megatron-style tensor parallelism), forgetting to insert an appropriate backward collective (no-op in forwards) will result in silently incorrect gradients. spmd_types keeps track of whether or backward gradients have pending reductions, allowing us to verify correct use of collectives. This is local SPMD typechecking.
  2. When writing distributed code, some functions have the same semantics no matter the choice of parallelism (e.g., "single device" code that trivially parallelizes), while other functions (e.g., "local map" regions) have semantics that change depending on the parallelism, as they are specifying computation that happens on a per-rank basis that doesn't commute with changes in sharding. A way to introduce a silent correctness is to write code without realizing it is not parallelism-invariant (e.g., doing a reduction on a sharded dimension, that requires a further distributed reduction.) If you are writing spmd_types you can explicitly specify if code is intended to be parallelism-invariant, and spmd_types will report if it's unable to prove that you've done this safely. As an auxiliary benefit, spmd_types SPMD type tells you how to reassemble the global tensor from the local shards. This is global SPMD typechecking.

We recently had Astra go through the Megatron codebase to look for silent distributed + numerical-correctness bugs, and it found 13, mostly around TP (Megatron-LM#7452), and most would've been catchable by spmd_types. Granted, this is not a huge number (we've seen comparable counts in our own codebases), we caught them in the midst of an MPU migration, and not all of them are in core production paths. Our thesis just is: it's easy to have these bugs in an active, ongoing codebase.

We also recently rewrote torchtitan to make use of spmd_types instead of DTensor, with the goal of making it more obvious when collectives occur in torchtitan model code. However, spmd_types is designed to be easy to retrofit in a variety of different codebases. In this post, we show how to integrate it with Megatron (but the learnings are applicable to any Megatron-style codebase.) The general recipe is:

  1. Make your codebase support fake process group, if it doesn't already. This allows you to run your full-size model code on a single GPU, which is good for testing and memory analysis. Megatron already supports this, so we just show what's needed for DSv3 compatibility.
  2. Write separate rules for annotating model inputs, parameters, and boundaries with appropriate types. This requires knowing a little bit about how distributed wrappers (e.g., FSDP) work. If you use stock PyTorch FSDP2 on PyTorch 2.14.0 or later, this is automatically handled for you. Megatron has a custom FSDP implementation, so in this post we'll show how it was adjusted to handle this.
  3. For each custom autograd function in your codebase, either decorate it with register_local_autograd_function (if it's a purely local autograd function and you only care about local SPMD typechecking) or add a static method spmd_typecheck describing its typing rule (if it's a distributed collective, or it's local but you want to do global SPMD typechecking). The registrations can live in a separate module imported at typecheck time, keeping them out of model code.
  4. Write a unit test (with fake PG) which runs your model code with typechecking enabled.

This patch specifically addresses the subset of changes needed to run DeepSeek-V3 in the recommended configuration as published by Megatron-Bridge.

Fake ProcessGroup setup & compatibility

PyTorch's fake ProcessGroup backend lets you simulate aspects of N-D parallel multi-GPU training runs using just 1 GPU, by replacing your collectives with stubs and no-ops. Numerics will be garbage and collective timing will be near-zero (see FakeProcessGroup.hpp), but you'll be able to realistically check per-rank memory usage and compute kernel runtime.

<code>spmd_types</code> only relies on operator sharding rule and input types, so by composing Fake PG + spmd_types, you can actually check correctness of the collectives you'd run at large scale. This helps ensure you're reducing TP gradients in the right places, treating activations as sharded when they are, using the right RNG seeds, without doing things like single-rank <-> large-scale numerics comparisons, cross-rank tensor hashing, or basing correctness off of a smaller-scale config.

You'd set up the 1 GPU as you would in a large-scale run, sharding weights and inputs at real degrees, run the FWD-BWD step on CUDA as usual - only difference is no collective communication shows up in your trace.

Parameter conventions

At the start of your typechecked FWD+BWD step, all inputs, params, buffers, and other involved tensors need annotations on the active mesh axes, as spmd_types works by intercepting ops and propagating output types.

TP annotations

From our experience, tensor parallelism, when applied broadly to your model, is arguably the most bug-prone parallelism, and where spmd_types helps the most. Most of the bugs in Megatron-LM#7452 are on TP, as it's not always obvious which tensors are sharded, which gradients need reducing when, etc. etc.

Typing along TP can be pretty involved, as all SPMD types show up (also see TorchTitan's sharding declarations as reference: https://github.com/pytorch/torchtitan/blob/50474ad6037cc0324f8db987243727e2988bc5e1/torchtitan/models/common/decoder_sharding.py#L197):

FWD sees different tokens, BWD needs reduction

For parameters, luckily Megatron stores attributes like tensor_model_parallel, partition_dim, sequence_parallel directly on params that helps us determine their annotations, so we can just translate.

Handling FSDP

Once your parameters and inputs (handled by tests) are annotated, you can try running typechecked FWD-BWD step. One of the first issues you'll probably run into is custom FSDP handling, as its machinery runs at each module's pre-forward, under typechecking scope.

If you're using PyTorch's stock FSDP2, from PyTorch 2.14.0 or later, this should be automatically handled for you, in a save-restore fashion - FSDP2 will read & save the original param annotations, shard for storage, and at pre-forward, hide its machinery from the typechecker, unshard, and restore annotations on the compute-ready params (following pytorch/pytorch#181519).

For custom FSDP implementations, the general FSDP guidance for local SPMD types basically recommends this - apply spmd.no_typecheck() liberally to hide internal machinery, and re-annotate after unshard, as how FSDP (or any analogous sharding mechanism) distributed params at rest, is orthogonal to compute-time sharding and outside of the autograd graph.

Annotating custom autograd functions

Assuming spmd_types doesn't find any distributed bugs, the next blocker you'll probably run into with Megatron is custom autograd Functions. spmd_types chooses not to propagate through these by default, because it's unclear if they'll perform collectives in FWD or BWD.

Local autograd functions

If you're only doing local SPMD typecheck, and you hit custom autograd.Fns that don't have collectives (e.g. they exist just to invoke custom BWD kernels - SwiGLU, MLA, RoPE, etc.), it's very easy to support - just annotate the autograd.Fn as local, and the typechecker knows to look inside them and apply standard local SPMD propagation rules.

These are op-invariant, standard rules like:

  • op(I) -> I: ranks computing on the same inputs produce the same outputs.
  • op(R) -> R
  • op(V) -> V: varying inputs, varying outputs.
  • op(R, V) -> V: one varying input, varying output. R is allowed to mix with V because the [R FWD <-> P BWD] duality means its gradients will be reduced, correctly aggregating contributions across ranks.

    For example, in data parallelism rank i computes hi=g(w,xi) from the shared weight w (R) and its own batch xi (V), and the loss L combines every rank's output. By the chain rule, the weight gradient is a sum with one term per rank:∂L∂w=∂L∂h1∂h1∂wrank 1+∂L∂h2∂h2∂wrank 2+⋯+∂L∂hN∂hN∂wrank NEach rank only computes its own term, so its local gradient for w is one summand of this sum, i.e. P. The gradient reduction gives the full global gradient.
  • op(I, V): error. I doesn't mix with any other type, as gradients won't be reduced. This requires a conversion to R first; convert(I -> R) in FWD is an all-reduce in BWD, performing the reduction.
  • linear_op(P) -> P, e.g. P + P -> P: a sum of partial sums is still a partial sum; this allows you to delay or coalesce all-reduces.
  • P + R, P + scalar: error, as the non-partial term gets summed once per rank.
  • nonlinear_op(P), op(P, V): error, reduce first. This is what reminds you when an all-reduce is needed (e.g. after colwise/rowwise TP FFN, before adding back to the residual stream).

The full local SPMD propagation rules table is at spmd_types documentation.

Every autograd.Fn called in a FWD-BWD pass needs type annotations. The typechecker only ensures the composition of functions is coherent for the FWD-BWD pass.

Writing custom autograd rules

Custom autograd.Fns are typechecking blackboxes, so if they perform collectives, the standard local SPMD rules probably don't apply. For such functions, we can write SPMD type rules, i.e. how the function changes types. This Megatron patch aims for least intrusiveness, so we keep the rules in the spmd_rules.py side-registry, but you could also define them inline as spmd_typecheck methods (see docs/rules.md).

Megatron defines its TP collectives in tp_mappings.py, custom autograd.Fns like _ReduceFromModelParallelRegion (P -> I), _ReduceScatterToSequenceParallelRegion (P -> S(seq)), which the spmd_types docs actually has a 1-1 mapping for. Registering these is pretty standard as they're just plain collectives, and the rules API actually has direct rules.all_reduce, rules.all_gather functions you can call, to signify e.g. the FWD behaves like a P -> I, S(i) -> R, etc.

class LinearWithFrozenWeight(torch.autograd.Function):
    """Linear operator that does not calculate gradient for weight.
    This op and LinearWithGradAccumulationAndAsyncCommunication performs
    mathematically-identical forward and DGRAD.

    Conceptually this op is the same as torch.nn.functional.linear with
    weight.requires_grad==False, but in experiments they are not identical
    mathematically."""

    @staticmethod
    @custom_fwd
    def forward(ctx, input, weight, bias, allreduce_dgrad, tp_group):
        """Forward with frozen weight."""
        ctx.save_for_backward(weight)
        ctx.allreduce_dgrad = allreduce_dgrad
        ctx.tp_group = tp_group
        output = torch.matmul(input, weight.t())
        if bias is not None:
            output = output + bias
        return output

    @staticmethod
    @custom_bwd
    def backward(ctx, grad_output):
        """Backward with frozen weight."""
        (weight,) = ctx.saved_tensors
        grad_input = grad_output.matmul(weight)

        if ctx.allreduce_dgrad:
            # All-reduce. Note: here async and sync are effectively the same.
            torch.distributed.all_reduce(grad_input, group=ctx.tp_group)

        return grad_input, None, None, None, None

    """See linear_with_grad_accumulation_and_async_allreduce"""

    @staticmethod
    @custom_fwd
    def forward(
        ctx,
        input,
        weight,
        bias,
        gradient_accumulation_fusion,
        allreduce_dgrad,
        sequence_parallel,
        grad_output_buffer,
        wgrad_deferral_limit,
        tp_group,
    ):
        """Forward."""
        if gradient_accumulation_fusion and hasattr(weight, "main_grad"):
            main_grad = weight.main_grad
        else:
            main_grad = None
        ctx.save_for_backward(input, weight)
        # We can't save main_grad in save_for_backward as this module would be
        # reused across layers like MTP logits. So, to prevent in-place modification
        # checks we save the tensor in ctx.
        ctx.main_grad = main_grad
        ctx.use_bias = bias is not None
        ctx.gradient_accumulation_fusion = gradient_accumulation_fusion
        ctx.allreduce_dgrad = allreduce_dgrad
        ctx.sequence_parallel = sequence_parallel
        ctx.wgrad_deferral_limit = wgrad_deferral_limit
        ctx.grad_output_buffer = grad_output_buffer
        ctx.tp_group = tp_group

        if sequence_parallel:
            dim_size = list(input.size())
            dim_size[0] = dim_size[0] * tp_group.size()

            all_gather_buffer = get_global_memory_buffer().get_tensor(dim_size, input.dtype, "mpu")
            dist_all_gather_func(all_gather_buffer, input, group=tp_group)
            total_input = all_gather_buffer
        else:
            total_input = input

        output = torch.matmul(total_input, weight.t())
        if bias is not None:
            output = output + bias
        return output

    @staticmethod
    @custom_bwd
    def backward(ctx, grad_output):
        """Backward."""
        input, weight = ctx.saved_tensors
        main_grad = ctx.main_grad
        use_bias = ctx.use_bias

class MoEAuxLossAutoScaler(torch.autograd.Function):
    """An AutoScaler that triggers the backward pass and scales the grad for auxiliary loss."""

    main_loss_backward_scale: Optional[torch.Tensor] = None

    @staticmethod
    def forward(ctx, output: torch.Tensor, aux_loss: torch.Tensor) -> torch.Tensor:
        """Preserve the aux_loss by storing it in the context to avoid garbage collection.

        Args:
            output (torch.Tensor): The output tensor.
            aux_loss (torch.Tensor): The auxiliary loss tensor.

        Returns:
            torch.Tensor: The output tensor.
        """
        ctx.save_for_backward(aux_loss)
        return output

    @staticmethod
    def backward(ctx, grad_output: torch.Tensor) -> Tuple[torch.Tensor, torch.Tensor]:
        """Compute and scale the gradient for auxiliary loss..

        Args:
            grad_output (torch.Tensor): The gradient of the output.

        Returns:
            Tuple[torch.Tensor, torch.Tensor]: The gradient of the output, scaled auxiliary loss
                                               gradient.
        """
        (aux_loss,) = ctx.saved_tensors
        if MoEAuxLossAutoScaler.main_loss_backward_scale is None:
            MoEAuxLossAutoScaler.main_loss_backward_scale = torch.tensor(
                1.0, device=aux_loss.device
            )
        aux_loss_backward_scale = MoEAuxLossAutoScaler.main_loss_backward_scale
        scaled_aux_loss_grad = torch.ones_like(aux_loss) * aux_loss_backward_scale
        return grad_output, scaled_aux_loss_grad

class CrossEntropyFunction(torch.autograd.Function):
    """
    This class implements a custom autograd function for the Cross Entropy loss. The input tensor can be in BF16/FP32, the
    loss and gradient calculation happens in FP32 only. The returned loss is always in FP32, the input gradients are upcasted
    to the dataype of the input.
    """

    @staticmethod
    def forward(
        ctx,
        inp,
        target,
        label_smoothing=0.0,
        reduce_loss=False,
        dist_process_group=None,
        ignore_idx=-100,
        is_cg_capturable=False,
    ):
        """
        The forward pass of the Cross Entropy loss. If dist_process_group is passed for distributed loss calculation, the input to each
        distributed rank should be (*,V/world_size). Note that each of the ranks should get equal shards along the V dimension.

        Parameters:
        ctx : The context object.
        inp (tensor): The input tensor of shape (B, SQ, V) or (SQ, B, V) where B is batch size, SQ is sequence length, V is vocab size.
        target (tensor): The target tensor of shape (B,SQ) or (SQ, B) where each value is in [0, V-1].
        label_smoothing (float): The amount of smoothing when computing the loss, where 0.0 means no smoothing.
        reduce_loss (bool): If true, returns the averaged loss across the B*SQ dimension.
        dist_process_group (torch.dist.ProcessGroup): The distributed process group the loss computation is split across, None if on 1 device.
        ignore_idx (int): The index for which loss and gradients are made to zero

        Returns:
        tensor: The computed loss.
        """
        loss, inp = triton_cross_entropy.cross_entropy_forward(
            inp,
            target,
            label_smoothing,
            reduce_loss,
            dist_process_group,
            ignore_idx,
        )

        ctx.save_for_backward(inp.detach())
        ctx.is_cg_capturable = is_cg_capturable
        return loss

    @staticmethod
    def backward(ctx, grad_output):
        """
        The backward pass of the Cross Entropy loss.

        Parameters:
        ctx : The context object with saved tensors.
        grad_output (tensor): The tensor containing the gradient of the loss with respect to the output.

        Returns:
        tuple: A tuple with the gradients with respect to the inputs. The elements are tensors or None.

Expert parallelism

For EP, Megatron uses what it calls "MoE parallel folding", which just means EP ranks are a subset of the (TP x CP x DP) GPU ranks, and not an orthogonal mesh axis (FWIW, torchtitan also does this).

It's then simpler to view EP vs. DP/CP/TP as on different device meshes, and not all on the same mesh, with the (TP x CP x DP) default dense mesh used for attention and other non-MoE-FFN compute, and the (ETP x EP x EDP) sparse or expert mesh for the MoE region.
