Using spmd_types in Megatron

spmd_types is a type system for distributed tensor computations. It helps solve two specific problems that commonly arise when writing distributed code:

  1. When using differentiable collectives (e.g., as popularized by Megatron-style tensor parallelism), forgetting to insert an appropriate backward collective (no-op in forwards) will result in silently incorrect gradients. spmd_types keeps track of whether or backward gradients have pending reductions, allowing us to verify correct use of collectives. This is local SPMD typechecking.
  2. When writing distributed code, some functions have the same semantics no matter the choice of parallelism (e.g., "single device" code that trivially parallelizes), while other functions (e.g., "local map" regions) have semantics that change depending on the parallelism, as they are specifying computation that happens on a per-rank basis that doesn't commute with changes in sharding. A way to introduce a silent correctness is to write code without realizing it is not parallelism-invariant (e.g., doing a reduction on a sharded dimension, that requires a further distributed reduction.) If you are writing spmd_types you can explicitly specify if code is intended to be parallelism-invariant, and spmd_types will report if it's unable to prove that you've done this safely. As an auxiliary benefit, spmd_types SPMD type tells you how to reassemble the global tensor from the local shards. This is global SPMD typechecking.

We recently rewrote torchtitan to make use of spmd_types instead of DTensor, with the goal of making it more obvious when collectives occur in torchtitan model code. However, spmd_types is designed to be easy to retrofit in a variety of different codebases. In this post, we show how to integrate it with Megatron (but the learnings are applicable to any Megatron-style codebase.) The general recipe is:

  1. Make your codebase support fake process group, if it doesn't already. This allows you to run your full-size model code on a single GPU, which is good for testing and memory analysis. (Megatron already supports this, so it is omitted in this post.)
  2. For each custom autograd function in your codebase, either decorate it with register_local_autograd_function (if it's a purely local autograd function and you only care about local SPMD typechecking) or add a static method spmd_typecheck describing its typing rule (if it's a distributed collective, or it's local but you want to do global SPMD typechecking). These registrations can live in a separate module that the SPMD typechecking tests load, keeping typechecking hooks out of model code.
  3. Write separate rules for annotating model inputs, parameters, and boundaries with appropriate types. This requires knowing a little bit about how distributed wrappers (e.g., FSDP) work. Megatron keeps these annotations in megatron.core.spmd.annotations; its custom FSDP/DDP wrappers state their own replication promises.
  4. Write a unit test (with fake PG) which runs your model code with typechecking enabled.

You can import spmd_types as spmd in each file that needs it, and keep each autograd function's registration or spmd_typecheck rule alongside its implementation, or, if you prefer keeping typechecking separate from compute definitions, you can maintain a separate rules registry module, only imported when typechecking tests run.

This patch specifically addresses the subset of changes needed to run DeepSeek-V3 in the recommended configuration as published by Megatron-Bridge.

Annotating custom autograd functions

Custom autograd functions are blackboxes to spmd_types’ typechecker; it can’t see the compute / collectives inside, and isn’t sure about the right propagation rules. Every autograd.Fn called in a FWD-BWD pass needs type annotations. These constitute trusted code: the typechecker doesn’t prove them right (by default - spmd.rulecheck can test them numerically), and correctness must be judged against the autograd.Fn’s runtime behavior. The typechecker only ensures the composition of functions is coherent for the FWD-BWD pass.

If you’re only doing local SPMD typechecking, it’s very simple to support custom autograd functions that don’t have collectives (e.g. SwiGLU, MLA, RoPE, router-gate, aux-loss) - just annotate the autograd.Fn as local, and the typechecker knows to apply standard local SPMD propagation rules.

The local SPMD propagation rules say things like:

  • I (Invariant: the FWD value and BWD gradient are identical across ranks) mixed with I gives I.
  • R (Replicate: identical FWD values, but gradients pend reduction) mixed with R gives R.
  • R combined with V (Varying: both FWD & BWD values can vary, e.g. sharded / different data / different local BS) gives V.
  • P (Partial: FWD pending reduction, identical incoming gradients) propagation depends on the class of op.

The full local SPMD propagation rules table is at spmd_types documentation.

Parameter conventions

TP annotations

All input tensors to a typechecked region (inputs / buffers / params) need annotation on all typechecking mesh axes. For Megatron this is (TP x CP x DP) for the dense mesh, and (ETP x EP x EDP) for the sparse (expert) mesh. PP is non-SPMD, so spmd_types doesn’t typecheck it.

Expert parallelism

For EP, Megatron uses what it calls MoE parallel folding: EP ranks are a subset of (TP x CP x DP) ranks, and it's simpler to view EP vs. DP x CP x TP as part of different meshes (different views of the same GPU ranks). The dense (TP x CP x DP) mesh is for attention and other non-expert-FFN compute, and the expert/sparse (ETP x EP x EDP) mesh for the MoE region.

spmd_types supports cross-mesh transitions: the mesh-axes in annotations are switched onto the new mesh, and the before/after types are verified to be compatible (if say, TP == ETP, a tensor is sharded on TP but not on ETP, spmd_types will raise, you must all-gather first).

Sparse/dense mesh transition happens at the dispatch/combine all2alls; routing is done on dense mesh, and the token sends to EP ranks transitions to sparse mesh. The expert_parallel_region / leave_expert_parallel_region runtime contexts tell the typechecker which mesh is currently active, but add no runtime overhead.
